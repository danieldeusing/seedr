Claude Code capability guide

Everything the Claude Code CLI reads, writes, and resolves — scopes, capability types, the two inheritance ceilings, and the bounded unknowns. Verified against the installed 2.1.226 bundle, not against vendor prose: where the shipped binary and a rolling documentation page disagree, the binary governs this version row and both sides are stated.

echo overview

The unit of analysis is the coding agent’s command-line executable plus the files and state that executable directly reads, writes, installs, or manages. CLI-native plugins, marketplaces, TUI features, remote-control entry points, and service-backed memory are in scope. VS Code and other IDE extensions, the desktop application, and web-only surfaces are out of scope even when they share a product name or an artifact path.

Every claim on this page carries an evidence class and a citation. Nothing here is added from memory or from a web search: if the source analysis does not state it, it is not on this page, and where the analysis records an unknown it is reproduced as an unknown with its U- number.

Binary evidence is asymmetric. A positive literal hit is strong evidence of support. An absence is only as strong as the extraction method, so every stated negative on this page names its method — "the literal appears only inside the sandbox configuration assembly", "no expression in the bundle joins the home directory to .mcp.json", and so on.

The five things most often gotten wrong, each corrected against the bundle and expanded further down:

  • There are two ceilings, not one. Instructions walk to the filesystem root's immediate child with no $HOME and no repository check; capability directories stop at $HOME (exclusive) or the repository root (inclusive), whichever comes first. S
  • ~/.claude.json is a resolver result, not a fixed path. S
  • ~/.mcp.json does not exist as an input. No expression in the bundle joins the home directory to that filename. S
  • .claude/hooks/ is never scanned — the joined literal sits in the sandbox write-protect path list (mechanism corrected this pass; the first pass attributed it to watcher cache invalidation), which is not registration either way. S
  • A skill is only ever a directory containing SKILL.md. A loose .md under skills/ is never loaded. S

The user JSON state file is a resolver result — S. It is not unconditionally ~/.claude.json. Instructions and rules — D. CLAUDE.md, .claude/CLAUDE.md and CLAUDE.local.md are Markdown delivered as user instruction context, not enforced policy. @path imports resolve relative to the containing file and recurse up to four hops; parsing ignores code spans and fenced blocks, and external project imports require approval. .claude/rules/**/*.md is recursive Markdown; an optional YAML paths glob list activates a rule when Claude reads a matching file, and a rule without paths is unconditional.

Effective content differs from disk — D/S. Block-level HTML comments in CLAUDE.md files are stripped before the content is injected into context; comments inside code spans and fenced blocks are preserved, inline comments within a paragraph are left intact, and an unclosed <!-- is left in place. A tool that renders what Claude Code actually loads must not assume the bytes on disk are the bytes in context. The comment-span regex is a 2.1.220 bundle literal. Three details matter and were previously stated loosely. (1) The anchor is the Git main checkout, not the repository the session sits in and not cwd; outside Git it falls back to the session project root. (2) The sanitizer is replace(/[^a-zA-Z0-9]/g, "-"), so /Users/x/Work/repo becomes -Users-x-Work-repo. (3) Long keys are truncated, not hashed wholesale — above 200 characters the key becomes the first 200 sanitized characters plus a base36 hash suffix. A scanner that assumes a pure 1:1 path-munge will miss long-path projects.

What it is — D/S. A skill is a directory containing a required Markdown SKILL.md, optionally accompanied by scripts, examples and resources. YAML frontmatter itself is optional; description is recommended and otherwise falls back to the first Markdown paragraph. Metadata is discovered first and the body loads only when the model selects it or the user invokes /name — progressive disclosure.

The directory-with-SKILL.md form is the ONLY form — S, bounded negative. Three independent code paths agree:

  • The runtime skills-directory loader filters readdir entries with if (!entry.isDirectory() && !entry.isSymbolicLink()) return null before joining SKILL.md, so a loose foo.md sitting directly in skills/ is never a skill.
  • The plugin-component enumerator uses readdir(...).filter(e => e.isDirectory()).map(e => join(dir, e.name, "SKILL.md")) for skills — versus a recursive *.md walk for commands.
  • The artifact classifier recognises a skill only at the exact four-segment shape .claude/skills/<name>/SKILL.md and returns null for anything else beneath skills/, including deeper nesting.

The filename literal joined is exactly SKILL.md. Case-insensitive matching (/^skill\.md$/i) appears only in the commands path, where a SKILL.md inside a command subdirectory renames the command after its directory. A SKILL.md above 1e6 bytes is skipped with a logged warning, and one that is not a regular file is skipped. A tool that also accepts loose .md files under skills/ will report capabilities Claude Code will not load.

This is the single most confusing part of Claude Code and the one most often gotten wrong. Claude's instruction walk and its capability walk are different loops with different stopping rules, and the capability ceiling is dual. A generic "nearest wins, stop at the repo root" model is wrong in both directions.

The instruction loop — S. The bundle builds the ancestor list with let p = cwd; while (p !== path.parse(p).root) { list.push(p); p = path.dirname(p) }, then reverses it so files concatenate root→cwd. Three asymmetries that break a naive edge model — S.

  1. The same directory name is not the same directory. Claude resolves its user tree through $CLAUDE_CONFIG_DIR, falling back to ~/.claude, while OpenCode's fallbacks are the literal paths ~/.claude/CLAUDE.md and ~/.claude/skills. With CLAUDE_CONFIG_DIR set, the two coding agents read different files under the same nominal name. Whether Copilot or OpenCode honors that variable is stated by no primary source — U-16.
  2. "Local" resolves differently. Claude canonicalizes .claude/settings.local.json to the Git main checkout; Copilot reads it project-relative. Inside a linked worktree the two designate different files.
