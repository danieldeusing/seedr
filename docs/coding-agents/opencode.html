OpenCode capability guide

Everything the opencode CLI reads, writes, and resolves — the two-binary V1/V2 split, the instruction selection rule that almost everyone states backwards, the git worktree ceiling, the ten configuration layers, every capability type, and the fact that merely loading this configuration writes to your disk. OpenCode is open source, so this page is anchored to the exact tag v1.18.16 and cross-checked literal-by-literal against the installed binary: where the tagged loader and a rolling documentation page disagree, the loader governs this version row and both sides are stated. Nothing here comes from memory or a web search.

which -a opencode opencode2 && opencode --version

Start here, because "OpenCode 1" and "OpenCode 2" are not two schemas of one program — they are two binaries. OpenCode 2 is a separate beta line. It installs from @opencode-ai/cli@next and runs as opencode2, and its own documentation is explicit that it does not replace OpenCode 1's opencode binary: both can stay installed and run side by side. Why this matters for a configuration browser. The two lines share the opencode.json / opencode.jsonc filenames and the same $schema URL, so a file gives you no version marker to read. A scanner that finds mcp.servers in a file has found an OpenCode 2 config that the installed opencode 1.18.16 will silently ignore — and one that finds mcp.<name> has found the opposite. Discriminate on shape, present the conclusion as an inference, and never assume one binary because one filename.

Ten claims that were documentation-shaped and are now source-verified. These had the right answer for the wrong reason; each is now backed by a named function rather than a page.

  • The AGENTS.md walk is merge-all within one filename class and first-match across classes — see the next section, which is the single most misread thing about OpenCode.
  • The walk ceiling is the Git worktree, inclusive, and "project root" is Git-defined only. Project.resolve returns repo.worktree from git rev-parse --show-toplevel, and returns the filesystem root with vcs: undefined when no .git exists above cwd.
  • The CLAUDE.md fallback conditions are exact — both halves, stated precisely in the ceiling section.
  • instructions resolution. Relative globs run per ancestor via globUp; absolute entries glob only their last segment; URLs are fetched separately at a 5 s timeout and appended after file results; and Instruction.system() re-runs inside the agent step loop.
  • JSON-defined agents and commands are first-class. ConfigV1.Info declares agent: Record<string, ConfigAgentV1.Info> and command: Record<string, ConfigCommandV1.Info> (plus deprecated mode), so a config file alone can define both. File discovery is an additional source, not the only one.
  • .opencode outranks the sibling top-level opencode.json, and rootmost outranks nearest inside .opencode, because the directory pass runs after the top-level pass and ConfigPaths.directories is not reversed while ConfigPaths.files is.

  • No hooks surface exists. No hooks path literal appears in the tagged source or the installed binary; plugin callbacks are the whole lifecycle contract.
  • Ancestor .opencode directories carry capabilities, not just instructions. ConfigPaths.directories feeds the command, agent, mode, plugin, skill and custom-tool loaders alike.

This is the most misunderstood thing about OpenCode, and the misunderstanding has a traceable origin. The rule is not "first match wins" and it is not "merge everything". It is both, on two different axes:

The rule, in one line. Merge-all WITHIN one filename class, first-match ACROSS classes. Every AGENTS.md from cwd through the worktree loads; only if none exists anywhere in that range does CLAUDE.md get a turn, and only if that class is empty too does deprecated CONTEXT.md.

Why both readings exist — S. Two pieces of code sit on top of each other and each contributes half the answer:

  • FSUtil.findUp(target, start, stop) contains no early exit. It appends join(current, target) for every level that has the file and stops only at stop or the filesystem root — so it returns all matches, nearest→root.
  • Instruction.systemPaths then runs matches.forEach(add) followed by break. That break ends the filename-class loop, not the ancestor walk.

The in-source comment is misleading, and it is the origin of the recurring wrong answer — S. The comment sitting directly above that block says, in substance, that the first project-level match wins so AGENTS.md/CLAUDE.md are not stacked from every ancestor. That sentence describes the class rule. The code beneath it stacks every ancestor of the winning class. Anyone who reads the comment and stops has the right words and the wrong algorithm — which is how "OpenCode takes the nearest AGENTS.md" became folklore.

Where the documentation diverges — D≠S. The rules page says the first matching file wins in each category, and lists only AGENTS.md and CLAUDE.md. The loader picks the first matching filename class and then loads every file in it, and additionally accepts undocumented CONTEXT.md. Two concrete consequences a tool must model:

  • A worktree-root AGENTS.md suppresses a closer CLAUDE.md. Distance loses to class.
  • Two ancestor AGENTS.md files both load. Neither shadows the other.

Ordering inside the resulting set — S. Insertion order: the global file first, then the project matches nearest→root, then the configured instructions. Nothing is replaced; everything accumulates.

The lazy descendant path is a second, different mechanism — S. When the Read tool opens a file below the session cwd, Instruction.resolve walks upward from that file's directory to — but excluding — the session directory. Not the worktree: the session directory. It attaches one nearby instruction per descendant directory, trying AGENTS → CLAUDE → CONTEXT at each. So this path can mix filename classes, which the startup path cannot.

A nearby instruction is skipped while its path already appears in the startup system paths, or in the loaded metadata of an earlier uncompacted completed Read call; a separate per-assistant-message claim set prevents duplicate attachment during concurrent or current-message reads.

For a configuration browser. Startup instructions and lazily attached ones are different sets with different rules. Only the startup set obeys the class rule; the descendant set is opportunistic, per-directory and per-read. Presenting them as one flat "instruction files" list states something false about both.

Every project walk in OpenCode stops at ctx.worktree, inclusive — the instruction walk, the top-level opencode.json walk, and the .opencode capability walk alike. And "project root" here has exactly one definition: Git. S

The permission model, stated — D/S. Actions are ask | allow | deny; a bare string permission normalizes to {"*": action}. The keys read, edit, glob, grep, list, bash, task, external_directory, lsp and skill — and any arbitrary extra key — accept either a single action or a pattern→action object, while todowrite, question, webfetch, websearch and doom_loop accept an action only. User key order is preserved for precedence — config is parsed with propertyOrder: "original", and the docs state the last matching rule wins. Agents carry their own permission override, and the agent-level tools map folds into it the same way as at config level (write/edit/patch → edit) with explicit permission winning.

Memory, as a bounded negative — S. Sessions, history, summary agents and compaction persist operational conversation state, but no first-party durable learned-memory file or configuration exists in the tagged loaders or in the config schema — nothing comparable to Claude auto memory or Copilot Memory. Semantic memory is plugin-provided if you want it. Session, share and server state is runtime-owned: treat it as opaque, do not parse it, do not offer to edit it.
