GitHub Copilot capability guide

Everything the copilot CLI reads, writes, and resolves — scopes, every capability type, the three precedence directions that run at once, the unusually wide .claude cross-read, and the bounded unknowns. Copilot CLI is closed source, so this page is verified against the shipped package @github/copilot 1.0.78: where a binary literal and a rolling documentation page disagree, the binary governs this version row and both sides are stated. Nothing here comes from memory or a web search.

copilot --version && copilot --help | head -1

Start here, because most Copilot advice on the internet is about a different product. "GitHub Copilot" is a brand over several loaders: the copilot CLI, the IDE extensions for VS Code / Visual Studio / JetBrains, and a set of cloud surfaces — the web coding agent, code review, Actions automation. They share a name and, in places, a file path. They do not share a loader.

This page documents the CLI only. That is the rule the source analysis applies throughout: "A product name may cover multiple loaders. Only claims about the named CLI executable belong in this report; a shared brand or path does not import IDE, desktop, web, code-review, or Actions behavior into the CLI model." Several widely repeated Copilot facts fail that test.

The six things most often gotten wrong, each corrected against the shipped package — or, for the last, against current CLI documentation — and expanded further down:

  • $COPILOT_HOME/config.json is not generated auth state. It is the legacy user settings file, and its values shadow the entire matching subtree of settings.json. S
  • Precedence runs three directions at once. Skills and agents are first-loaded-wins, MCP is last-loaded-wins, hooks all run, settings are ranked. A single "nearest wins" rule is wrong three different ways. S
  • applyTo instruction files and nested AGENTS.md are advertised, not concatenated. They are rendered as a table the model fetches from on demand. S
  • .vscode/mcp.json support was removed and the path is now detected only to emit a migration notice. S
  • There are two plugin CLIs — copilot plugin and a separate cross-kind copilot plugins. S
  • .claude/commands/*.md and .claude/CLAUDE.md are documented CLI read locations after all — both were withdrawn to U on the first pass, and both were restored to D on the second: current CLI pages state each, and stated it before the first pass's cutoff. Self-update is a provenance hazard — S, plus O for the payload cache. copilot update [channel] with stable (default) and prerelease channels; on-startup auto-update on by default; the autoUpdate setting (defaults to true); COPILOT_AUTO_UPDATE=false or --no-auto-update to disable; auto-update disabled by default in CI environments (detected via CI, BUILD_NUMBER, RUN_ID or SYSTEM_COLLECTIONURI); downloaded payloads cached under $COPILOT_HOME/pkg/<platform>/<version>/ (13 historical payloads, 0.0.393–1.0.40, observed under pkg/universal/ on 2026-08-13). $COPILOT_HOME and how it resolves — S. COPILOT_HOME replaces the CLI's default ~/.copilot root; COPILOT_CACHE_HOME independently replaces the platform cache. The older --config-dir flag is deprecated in favour of it — installed help reads "Path to the configuration directory (deprecated: use COPILOT_HOME env var)" — and every consumer of the root resolves the same expression:

t?.configDir ?? process.env.COPILOT_HOME ?? join(homedir(), ".copilot")

The repository settings rank map — S. Repository settings are two files with an explicit numeric rank, and the rank is the thing to encode, not the filenames:

{repo: ".github/copilot/settings.json", local: ".github/copilot/settings.local.json"}
{user: 0, repo: 1, local: 2}   // higher wins

Rank 2 — .github/copilot/settings.local.json — is the top of the ordinary file tiers, and it is gitignored by intent. Rank 0, the user tier, is two files rather than one, which is what the next-to-last row of the corrections table is about. Repository settings accept only a documented subset of keys; some values are union- or tighten-only, and managed security controls can remain non-overridable regardless of rank — D: the configuration-directory reference states "Only the keys listed in the following table are supported at the repository level. Any other keys—including keys that are valid in the user configuration file—are silently ignored", lists the 14 supported keys (companyAnnouncements, contextTier, deniedUrls, disableAllHooks, disabledMcpServers, disabledSkills, effortLevel, enabledPlugins, extraKnownMarketplaces, hooks, includeCoAuthoredBy, mergeStrategy, model, respectGitignore), and marks per-key semantics Union (add, never remove: deniedUrls, disabledMcpServers, disabledSkills), Tighten-only (respectGitignore) and Replaced (model, effortLevel, contextTier — applying only when the working directory is trusted).
