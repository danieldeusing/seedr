Cross-tool capability matrix

The axis five per-agent guides structurally cannot hold. “Which of the five read AGENTS.md?” is a question about the columns, and each guide keeps only its own row. This page restores the columns: one exhaustive artifact matrix, the inheritance and precedence directions side by side, the vocabulary traps, the U-01 … U-16 register, and the change-risk ranking. Every fact here is re-sourced from the five guides after their second verification pass — not from the retired analysis this page replaces.

echo 'the axis a per-agent split destroys'

Five guides document five command-line coding agents — Claude Code, OpenAI Codex, GitHub Copilot, OpenCode and Google Antigravity — one page each. That split is right for depth and wrong for one specific question: which of the five read this file? That question runs across the columns, and a per-agent page keeps only its own row. This page is the columns.

The unit of analysis is unchanged: the coding agent’s command-line executable plus the files and state that executable directly reads, writes, installs, or manages. IDE extensions, desktop applications and web-only surfaces are out of scope even when they share a product name or an artifact path — which matters more here than anywhere, because three of the five brands cover several loaders and most of the interoperability folklore on the internet is about the wrong one.

Model the edge, not the folder. One physical artifact has zero or more agent-reader relationships, each carrying its own evidence class, walk, ceiling and assembly rule. Compatibility is assigned per artifact and never to .claude/, .agents/ or .github/ wholesale. Cloning one file into five independent logical artifacts loses the edges; collapsing five readers into one loses the differences that break tools.

Two cells can read R for one coding agent and U or D for another on the same path. That is intended: evidence strength is per reader, and no matrix cell is allowed to claim more than the per-agent guide behind it.

Note A path with no documented reader is unsupported, not deleted. Represent it as unsupported or unknown rather than removing it merely because one coding agent does not consume it — four coding agents share the .agents/ tree and two share .mcp.json.

The file is portable; the effect is not. Four coding agents read one AGENTS.md with four different ceilings and three genuinely different assembly rules: Codex orders root→cwd inside a hard project ceiling and truncates the closest file first when its shared 32 KiB budget runs out; Copilot concatenates unconditional sources with no published precedence while advertising nested ones on demand; Antigravity accumulates cwd→repository root with resolved-path de-duplication; OpenCode loads every match of the winning filename class up to the git worktree.

Trap “OpenCode also reads CLAUDE.md” is true only in the negative case. A single AGENTS.md at any level between cwd and the worktree suppresses every project CLAUDE.md at startup — distance loses to filename class. A browser listing it as an active instruction source is showing a file that never enters the context.

The four differences that bite.

  • Claude's dual ceiling is one helper across six capability types. The shared function — its own log line names it getProjectDirsUpToHome — halts before $HOME without collecting it, collects a directory that is the repository ceiling and then stops, and reaches the filesystem root only when neither fires. So ~/.claude/skills is never a project directory, while a CLAUDE.md in the home directory is read as an ordinary ancestor. Those look contradictory only if the two walks are conflated.
  • Codex searches up and orders down, and the project root is a hard ceiling. Reading it as “walk up from cwd, nearest wins” produces exactly the reverse order — and because the 32 KiB budget drains root→cwd, it is the closest file, the one a reader most expects to be authoritative, that truncates first.
  • OpenCode is merge-within-class and first-match-across-classes, with a rootmost-wins capability walk. A worktree-root AGENTS.md suppresses a closer CLAUDE.md; two ancestor AGENTS.md files both load; and for anything under .opencode the file furthest from your working directory wins — the exact opposite of Claude's nearest-wins capability walk, from a directory layout that looks identical. There is no explicit “rootmost wins” statement anywhere in the product: the behavior is the consequence of one missing reverse().
  • Copilot's MCP walk is trust-gated and one-file-per-directory. It ascends cwd→Git root, takes the first existing of .mcp.json then .github/mcp.json at each level, and stops early at any directory that fails the folder-trust predicate. Depth 0 is tagged project; everything above is tagged inherited.

“Local” is not one file Claude canonicalizes .claude/settings.local.json to the Git main checkout; Copilot reads the same filename project-relative. Inside a linked worktree the two coding agents designate different files under one name. Codex redirects hook discovery the other way — config from the worktree, hooks from the main checkout — so a scanner reporting one project path for both is wrong, and the hooks half is the one that executes commands.

Plugin lifecycle Claude version pinning and reload boundaries (mid-session updates keep old hook, MCP and LSP paths until /reload-plugins); Codex's two manifest resolvers with different orders plus a startup marketplace refresh that mutates the cache with no command; Copilot's two plugin CLIs and a marketplace update distinct from a plugin update; Antigravity's root conflict and missing update verb; OpenCode's cached identity being the package name irrespective of version. “Up to date” is not computable from a config file in three of the five
Hook and policy semantics Parallel (Claude), concurrent (Codex), all-run with restrictive dominance (Copilot), sequential and blocking (Antigravity) — and nonexistent (OpenCode). Ownership requirements on Copilot policy files, three accepted matcher formats in one registry, and an Antigravity working directory that changes with the file's own location
MCP credentials and replacement Five different files, schemas, auth stores and duplicate-ID behaviors. Same-name replacement is whole-server in Claude, per-key deep-merge with wholesale array replacement in Codex, last-loaded-overlay in Copilot. Copying a server entry mechanically can leak secrets or silently change the tool set — and Codex rejects an inline bearer_token outright
Remote and cloud commands Claude and Codex distinguish local remote control from cloud execution; Copilot Remote Control keeps execution local while /delegate does not. These states are operational, authenticated and not portable config. Two of the five expose an entry point that is absent from --help
Moderate Instruction ordering “Nearest wins” is wrong for Claude (concatenation), wrong for Codex (root→cwd, closest truncated first), wrong for Copilot (no order at all), and wrong for OpenCode twice over — class before distance, and opposite directions for top-level config and structured directories in the same repository
Agents and skills Similar Markdown filenames conceal incompatible schemas, field support, isolation and duplicate rules. Codex agents are TOML while everyone else's are Markdown; Copilot's .agent.md and plain .md coexist by root inside one product; required frontmatter differs in all five
Inventing a local scope Only some CLIs have a documented private-project override, and two absences are now source-proven rather than merely undocumented: no config.local.toml anywhere in Codex, no opencode.local.json in source or binary. Synthesizing one produces a dead file
Withdrawn and restored capabilities The evidence itself moves between passes. $CODEX_HOME/prompts was demoted from a documented reader to unverified; Copilot's .claude/commands and .claude/CLAUDE.md were withdrawn and then restored. Scanning an unproven path is harmless; reporting it as live is not
Antigravity's own contradictions Shared-versus-private roots require an explicit version and confidence state in any UI. The SKILL.md-versus-flat-file question is settled in favour of directories, so a tool should stop offering the flat shape. The workspace mcp_config.json and the workflow directory are the live version-sensitive gaps
Lower, not zero Presentation-only files Keybindings, themes and status lines have little cross-tool ownership but still need schema and version validation — and OpenCode themes are not scope-bounded like the rest of its capabilities: their walk ignores the worktree ceiling and runs to the filesystem root, so a theme far above the project can win
Deleting an unread path A path with no documented reader is unsupported, not deleted. Four coding agents share the .agents/ tree, two share .mcp.json, and every bounded negative on these pages is scoped to one version row and one extraction method

Which conventions look newest and least stable. The .agents/ namespace is the youngest and the most contested: only skills is genuinely shared, Codex uses two exact marketplace filenames beneath .agents/plugins/ that are a different contract entirely, and every other child is an Antigravity-only path that three binaries have no literal for. Plugin manifest compatibility is next — four products accept each other's manifest layouts within a supported field subset, and the two most recent corrections in this corpus both landed there (Codex's root-first probe, Copilot's runtime-assembled manifest paths). Anything a scanner encodes about those two areas should carry a version and be re-checked on the next release.
